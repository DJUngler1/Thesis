Linter- und Formatter-Konventionen

Dokumentation der Werkzeugauswahl für Schritt 2 des Code-Analysis-Tools

Autor:in

Felix Krauß

Veröffentlichungsdatum

7. November 2026

1 Zweck und Vorgehen

Dieses Dokument hält fest, welche Formatter und Linter das Code-Analysis-Tool in Schritt 2 („Install linter / formatter: Fixed rules per language“) für jede unterstützte Sprache einsetzt. Zu jeder Festlegung steht, warum sie getroffen wurde und wie sie überprüft wurde. Die knappe technische Festlegung ohne Begründungen liegt im Tool-Repository unter Code-Analysis-Tool/docs/linterConventions/README.md.

1.1 Grundsatz der Festlegung

  • Default-Stil: Für jede Sprache wird der Standardstil eines etablierten Werkzeugs verwendet, mit möglichst wenig eigener Konfiguration. Eigene Abweichungen gibt es nur bei C/C++ (vier clang-format-Optionen und eine feste clang-tidy-Check-Liste).
  • Projektkonfiguration wird ignoriert: Die Konfigurationsdateien des analysierten Projekts werden immer ignoriert, damit die Ergebnisse verschiedener Projekte vergleichbar sind (siehe Kapitel 9).
  • Sprachversion wird übernommen: Die Sprachversion des Projekts (Java-Version, Python-Version, C++-Standard) ist keine Konfiguration im Sinne dieses Grundsatzes. Sie wird aus dem Projekt übernommen, weil die Werkzeuge sonst Code falsch lesen oder fehlerhaften Code erzeugen (siehe Kapitel 6.4 und Kapitel 4.3.3).
  • Geprüfte Arbeitskopie: Die Formatter verändern Dateien direkt. Schritt 1 nimmt deshalb nur Projekte mit sauberem Git-Arbeitsverzeichnis an, sodass jede Änderung mit git diff nachvollzogen und zurückgenommen werden kann.

1.2 Prüfmethode

  1. Dokumentation im Original: Jede Aussage über ein Werkzeug wurde in dessen offizieller Dokumentation nachgelesen. Zitate sind wörtlich und stehen in der Originalsprache (Englisch).
  2. Eigene Tests: Das Verhalten wurde am 07.11.2026 in Docker-Containern mit festen Werkzeugversionen getestet (Tabelle 1).
  3. Art der Testprojekte: Die Tests liefen auf kleinen, eigens angelegten Beispieldateien, die gezielt einzelne Fälle enthalten. Sie zeigen, wie sich ein Werkzeug verhält, sagen aber nichts darüber, wie viele Befunde auf echten Projekten entstehen oder wie viele davon Fehlalarme sind (siehe Kapitel 10).

1.3 Testumgebung

Die Versionen sind festzuschreiben, weil sich Standardregeln und Standardstile zwischen Versionen ändern. Ruff aktiviert in Version 0.17.4 zum Beispiel 407 Regeln standardmäßig (siehe Kapitel 6).

2 Übersicht der Festlegungen

Sprache Werkzeuge Befehle (in dieser Reihenfolge)
C# dotnet format dotnet format (mit ausgeblendeter .editorconfig)
Java google-java-format, PMD google-java-format --replace, dann pmd check … --use-version java-<Projektversion>
JavaScript, TypeScript Biome biome check --write --config-path=<projekt>/.code-analysis-biome.json --vcs-use-ignore-file=true …
Python Ruff ruff check --fix --isolated --target-version py3X, dann ruff format --isolated --target-version py3X
C, C++ clang-format, clang-tidy clang-format -i --style=…, dann clang-tidy … --config=… (ohne --fix)
Rust Clippy, rustfmt cargo clippy --fix --allow-dirty, dann cargo fmt (jeweils mit eigener Konfiguration des Tools)

Platzhalter in den Befehlen:

  • <projekt> ist der Ordner des analysierten Projekts.
  • <output> ist der Ausgabeordner des Tools außerhalb des Projekts.
  • <tool> ist ein Ordner im Container des Tools mit eigenen, leeren Konfigurationsdateien.

3 C

3.1 Festlegung

dotnet format, ausgeführt im Ordner mit der Solution- oder Projektdatei, ohne eigene Konfiguration. Die .editorconfig-Dateien des Projekts werden während des Laufs ausgeblendet.

3.2 Begründung und Belege

  • Was das Werkzeug tut. dotnet format gehört zum .NET SDK. Die Dokumentation beschreibt es als „a code formatter that applies style preferences and static analysis recommendations to a project or solution. Preferences will be read from an .editorconfig file, if present, otherwise a default set of preferences will be used.“ [MS-format]. Ohne Konfiguration gilt also Microsofts Standard für .NET.
  • Nur ab Schweregrad warning. dotnet format behebt nur Diagnosen ab diesem Schweregrad: „The minimum severity of diagnostics to fix. […] The default value is warn.“ [MS-format]
  • Wenige Regeln ohne Konfiguration.
    • Code-Style-Regeln (IDExxxx) sind beim Build über die Kommandozeile standardmäßig abgeschaltet: „Code-style analysis is disabled, by default, for all .NET projects on command-line builds.“ [MS-analysis]
    • Bei den Code-Quality-Regeln (CAxxxx) sind im Standardmodus „only a small number of rules […] enabled as build warnings“ [MS-analysis], in .NET 10 sind es 29.

3.3 Testergebnisse

  • Ohne Konfiguration:
    • Geändert: Die Formatierung wurde vollständig angepasst: geschweifte Klammern in eigener Zeile, Einrückung mit 4 Leerzeichen, Leerzeichen um Operatoren. Außerdem wurde throw e; zu throw; (Regel CA2200).
    • Nicht geändert: Die ungenutzten using-Direktiven blieben stehen.
    • Folgerung: Ohne Konfiguration ist dotnet format vor allem ein Formatter mit wenigen Analyzer-Korrekturen und kein vollständiger Linter.
  • Mit Projektkonfiguration: Eine .editorconfig des Projekts (2 Leerzeichen, Klammern in derselben Zeile) wurde befolgt. Nach dem Ausblenden der Datei galt der Standard.

3.4 Grenzen

  • Analyzer-Einstellungen in der Projektdatei bleiben wirksam. Mit <AnalysisMode>All</AnalysisMode> in der .csproj machte dotnet format aus public class ein internal class und entfernte ein ungenutztes Feld, auch bei ausgeblendeter .editorconfig. Ohne diese Einstellung änderte es nur die Formatierung. Abschalten lässt sich das nur, indem man die Projektdatei verändert.
  • Projektcode wird ausgeführt. „dotnet format may restore, compile, and run analyzers from the specified project or solution. Only invoke the tool against trusted code.“ [MS-format] Das Werkzeug läuft deshalb im Container.

4 Java

4.1 Festlegung

java -jar google-java-format-<version>-all-deps.jar --replace <alle .java-Dateien>

pmd check -d <projekt> --exclude <projekt>/target --exclude <projekt>/build \
  -R rulesets/java/quickstart.xml --use-version java-<Projektversion> \
  --no-fail-on-violation --no-cache --no-progress \
  -f sarif -r <output>/pmd.sarif

4.2 google-java-format (Formatter)

  • Stil. „google-java-format is a program that reformats Java source code to comply with Google Java Style.“ Es ist „an opinionated formatter with very little configuration“ [GJF]. Die einzige Stil-Alternative --aosp (4 Leerzeichen Einrückung) wird nicht verwendet.
  • Imports. Standardmäßig sortiert es Imports und entfernt ungenutzte Imports. Beides lässt sich mit --skip-sorting-imports und --skip-removing-unused-imports abschalten [GJF].
  • Test.
    • Das Werkzeug stellte auf 2 Leerzeichen Einrückung um, setzte eine Anweisung pro Zeile und ergänzte geschweifte Klammern.
    • Es entfernte den ungenutzten Import java.util.Map.
    • Eine ungenutzte lokale Variable blieb stehen: google-java-format meldet keine Regelverstöße, es formatiert nur.
  • Voraussetzung. Benötigt wird ein JDK (kein JRE), mindestens „currently Java 21“, und „a version equal to or newer than the Java language version of the files being formatted“ [GJF]. Der Java-Container muss deshalb das neueste JDK enthalten, nicht das in den Tests verwendete JDK 21.

4.3 PMD (Linter)

4.3.1 Auswahl gegenüber Checkstyle

PMD wurde gewählt, weil google-java-format selbst keine Befunde liefert. Als Alternative wurde Checkstyle mit der mitgelieferten Konfiguration google_checks.xml getestet. Das ist die „Checkstyle configuration for ‘Google Java Style’“ [CS-google], passt also zum Stil von google-java-format. Beide liefen auf derselben, zuvor von google-java-format formatierten Beispieldatei:

Die drei nur von PMD gefundenen Befunde sind echte Fehler. Checkstyle meldete zusätzlich nur Stilabweichungen gegenüber dem Google-Styleguide. Checkstyle-Befunde, die google-java-format widersprochen hätten, gab es auf der formatierten Datei nicht.

4.3.2 Regelsatz

quickstart ist PMDs mitgelieferter Regelsatz: „Quickstart configuration of PMD. Includes the rules that are most likely to apply everywhere.“ [PMD-rules]

4.3.3 Java-Version

PMD muss den Code mit der Java-Version lesen, für die er geschrieben ist. PMD 7.29.0 kennt die Versionen 1.3 bis 27. „Usually the latest non-preview Java Version is the default version.“ [PMD-java] In 7.29.0 ist das Java 27.

  • Test mit altem Code. Java-1.4-Code, der enum als Variablennamen verwendet, konnte mit der Standardversion nicht gelesen werden („Encountered “++”“). Mit --use-version java-1.4 wurde er analysiert.
  • Test mit Preview-Feature. Ein Preview-Feature (primitive Typen in instanceof) wurde ohne passende Preview-Version abgelehnt. PMD unterstützt Preview-Features nur eingeschränkt: „we only support preview language features for the latest two java versions.“ [PMD-java]

Das Tool liest die Version deshalb aus der Build-Datei:

Build-Datei Fundstelle der Version (erster Treffer gilt)
pom.xml (Maven) maven.compiler.release bzw. <release>, sonst maven.compiler.source bzw. <source> [Maven-compiler]
build.gradle(.kts) (Gradle) java { toolchain { languageVersion = JavaLanguageVersion.of(N) } }, options.release = N oder sourceCompatibility [Gradle-toolchains]
  • Version N gefunden: Das Tool übergibt --use-version java-N.
  • Preview aktiviert (--enable-preview): Das Tool übergibt java-N-preview.
  • Keine Version gefunden: Das Tool übergibt keine Version, und PMD nutzt seine Standardversion. Das passiert auch, wenn die Version nur indirekt gesetzt ist, etwa in einem Parent-POM.
  • Version, die PMD nicht kennt: PMD bricht mit einem Bedienfehler ab und schreibt keinen Bericht (getestet mit java-28: „Unknown language version: java-28“). Das Tool startet PMD dann ohne --use-version neu und vermerkt das im Bericht.

4.3.4 Verhalten im Test

  • Nicht lesbare Dateien.
    • PMD überspringt sie und analysiert den Rest weiter.
    • Im SARIF-Bericht erscheinen sie unter invocations[].toolExecutionNotifications mit Dateipfad, und executionSuccessful ist false.
    • In der Textausgabe meldete PMD für eine solche Datei „Found no violations. There was 1 processing error.“ Das Tool muss diese Dateien deshalb im Bericht aufführen, sonst sehen sie wie befundfreie Dateien aus.
  • Exit-Codes [PMD-CLI]:
    • 0: Lauf ohne Fehler; Befunde stehen im Bericht. Ohne --no-fail-on-violation wäre der Code bei Befunden 4. Beides getestet.
    • 5: „At least one recoverable error has occurred“, etwa eine nicht lesbare Datei (getestet).
    • 1 und 2: Abbruch mit Ausnahme bzw. ungültige Parameter (laut Dokumentation, nicht getestet).
  • Build-Ausgaben. Mit --exclude wurde eine Java-Datei unter target/generated-sources nicht analysiert.
  • Lombok. Private Felder einer mit @Getter annotierten Klasse wurden nicht als ungenutzt gemeldet, obwohl die Lombok-Bibliothek fehlte.

4.3.5 Grenze: Typinformationen

PMD analysiert den Quelltext, ohne das Projekt zu bauen. Ohne die Abhängigkeiten des Projekts im „auxclasspath“ gilt: „Not providing the correct auxClasspath might result in false positives or negatives for some rules“ [PMD-java]. Das Tool baut Java-Projekte in Schritt 2 bewusst nicht. Ein Build bräuchte das passende JDK und Netzwerkzugriff und würde die Build-Plugins des Projekts ausführen.

5 JavaScript und TypeScript

5.1 Festlegung

npx @biomejs/biome@<version> check --write \
  --config-path=<projekt>/.code-analysis-biome.json \
  --vcs-enabled=true --vcs-client-kind=git --vcs-use-ignore-file=true \
  --reporter=sarif --reporter-file=<output>/biome.sarif .

Ablauf eines Laufs:

  1. Das Tool verschiebt alle biome.json- und biome.jsonc-Dateien des Projekts aus dem Projekt heraus.
  2. Es legt im Projektordner die Datei .code-analysis-biome.json an. Sie enthält nur {}, sodass Biomes Standardwerte gelten.
  3. Biome läuft. Dateien und Ordner aus den .gitignore-Dateien des Projekts (auch verschachtelten) werden dabei nicht geprüft.
  4. Danach löscht das Tool .code-analysis-biome.json und legt die Projektdateien zurück.

Warum der Ablauf so aussieht, steht in Kapitel 5.4.

5.2 Begründung und Belege

  • Was check tut. biome check „Checks the specified files for formatting, linting, and assist actions“. --write „Applies formatting changes, safe lint fixes, and safe assist actions.“ [Biome-CLI]
  • Kein Konfigurationszwang. „If no configuration is found, Biome’s default configuration is used.“ [Biome-configure]
  • Standardwerte [Biome-ref]:
    • Einrückung mit Tabs, Zeilenbreite 80, doppelte Anführungszeichen;
    • die empfohlenen Lint-Regeln.

5.3 Testergebnisse

  • Geändert: Biome stellte die Einrückung auf Tabs und die Anführungszeichen auf doppelte um, ergänzte Semikolons und sortierte die Imports.
  • Nicht geändert: Unsichere Korrekturen wendet Biome nicht an.
    • x == 1 blieb stehen, weil die Korrektur zu === als unsicher gilt.
    • Eine ungenutzte Variable blieb ebenfalls stehen.
    • Biome meldete „Skipped 5 suggested fixes“. Erst --unsafe würde diese Korrekturen anwenden [Biome-CLI].
  • Exit-Code.
    • Biome bearbeitet erst alle Dateien und endet dann mit Code 1, wenn Befunde vom Schweregrad error übrig bleiben.
    • Eine Option, trotzdem mit 0 zu enden, gibt es in 2.6.6 nicht. check --help bietet nur --error-on-warnings („Exits with an error status if any warning diagnostics are emitted.“), das strenger macht.
    • Code 1 kam auch bei kaputter biome.json, unbekannter Option und leerem Ordner. Der Exit-Code allein unterscheidet also nicht zwischen „Befunde übrig“ und „Biome ist gescheitert“.
  • Bericht statt Exit-Code.
    • Mit --reporter-file stehen alle nicht behobenen Befunde mit Regel, Schweregrad, Datei und Zeile im Bericht.
    • Bei kaputter biome.json wurde kein Bericht geschrieben. Das Tool wertet den Lauf deshalb anhand des Berichts aus.
  • SARIF statt JSON. Biome meldet selbst: „The json and json-pretty reporters are experimental and may change in patch releases.“ Verwendet wird deshalb SARIF 2.1.0.
  • Bericht außerhalb des Projekts. Als ein Bericht im Projektordner lag, prüfte Biome ihn im selben Lauf mit und meldete ihn als fehlerhafte Datei.
  • Projektkonfiguration.
    • --config-path „Sets the path to the configuration file or the directory where Biome should search for biome.json or biome.jsonc. This option disables the default configuration file resolution.“ (biome check --help)
    • Testprojekt: eine biome.json im Projekt (4 Leerzeichen, noDoubleEquals aus), eine verschachtelte pkg/biome.json (6 Leerzeichen) und eine .editorconfig (8 Leerzeichen).
    • Tool-Konfiguration außerhalb des Projekts: Zeigte --config-path auf einen Ordner außerhalb des Projekts mit {}, wirkte keine der drei Dateien. Alles wurde mit Tabs formatiert, und noDoubleEquals wurde überall gemeldet.
    • Tool-Konfiguration im Projekt: Lag die Datei mit {} im Projektordner (nötig für .gitignore, siehe Kapitel 5.4), wurde die Projektdatei biome.json weiterhin ignoriert. Die verschachtelte pkg/biome.json wirkte aber wieder: pkg/b.ts wurde mit 6 Leerzeichen eingerückt. Deshalb verschiebt das Tool alle biome.json- und biome.jsonc-Dateien vor dem Lauf aus dem Projekt.
    • Die .editorconfig wirkte in keinem Fall.

5.4 Ordner aus .gitignore ausschließen

5.4.1 Problem

Biome liest .gitignore standardmäßig nicht (vcs.useIgnoreFile ist standardmäßig false [Biome-ref]). Im Test formatierte Biome ohne Zusatzoptionen dist/out.js um, obwohl dist/ in der .gitignore stand. node_modules wurde übersprungen. Build-Ausgaben und andere von Git ignorierte Dateien sollen aber nicht formatiert werden.

5.4.2 Optionen

--vcs-use-ignore-file „Controls whether Biome applies patterns from .gitignore, Git’s local .git/info/exclude, and supported .ignore files, including nested ignore files. Patterns in the root ignore file are resolved from vcs.root.“ Sie setzt --vcs-enabled=true und --vcs-client-kind=git voraus (biome check --help). Ohne eigene Konfiguration blieb dist/ mit diesen Optionen unverändert.

5.4.3 Konflikt mit einer Konfiguration außerhalb des Projekts

vcs.root wird relativ zum Ordner der Konfigurationsdatei aufgelöst: „A relative value is resolved from the directory containing the current configuration file, while an absolute path is used directly.“ (biome check --help). Liegt die Tool-Konfiguration außerhalb des Projekts, sucht Biome die .gitignore deshalb dort:

In keinem der beiden Fehlerfälle wurde ein Bericht geschrieben. Die Erfolgsprüfung über den Bericht erkennt sie also.

5.4.4 Getestete Lösung

Getestet wurde der Ablauf aus der Festlegung: alle biome.json/biome.jsonc aus dem Projekt verschoben, .code-analysis-biome.json mit {} im Projektordner, VCS-Optionen gesetzt.

  • Ausgeschlossen: dist/ aus der .gitignore im Projektordner und pkg/gen/ aus einer verschachtelten pkg/.gitignore blieben unverändert.
  • Formatiert und geprüft: Die übrigen Dateien wurden mit Biomes Standardwerten formatiert (Tabs), und noDoubleEquals wurde in beiden Quelldateien gemeldet. Der SARIF-Bericht wurde geschrieben.
  • Ohne .git-Ordner: Das funktionierte auch in einem Ordner ohne .git. Biome liest also nur die Ignore-Dateien und braucht kein Git-Repository.
  • Aufräumen: Nach dem Lauf wurden die verschobenen Dateien zurückgelegt und die eigene Datei gelöscht.

Mit .gitignore liest Biome bewusst eine Datei des Projekts. Sie bestimmt aber nur, welche Dateien zum Quellcode gehören, nicht wie sie geprüft werden. Der Grundsatz aus Kapitel 9 bleibt damit gewahrt.

6 Python

6.1 Festlegung

ruff check --fix --isolated --target-version py3X .
ruff format --isolated --target-version py3X .

py3X ist die Untergrenze von requires-python in der pyproject.toml des Projekts, zum Beispiel wird >=3.8 zu py38. Ohne Angabe entfällt --target-version.

6.2 Begründung und Belege

  • Formatter. ruff format ist ein Ersatz für Black: „the formatter is intended to emit near-identical output when run over existing Black-formatted code“ [Ruff-formatter]. Die Standardwerte sind Zeilenlänge 88, Einrückung 4, doppelte Anführungszeichen und Einrückung mit Leerzeichen [Ruff-settings].
  • Nur sichere Korrekturen. „Ruff only applies safe fixes by default.“ [Ruff-linter]
  • Reihenfolge Linter vor Formatter. „To sort imports and format, call the Ruff linter and then the formatter“ [Ruff-formatter]. Lint-Korrekturen können Code hinterlassen, der neu formatiert werden muss.
  • Standardregeln. Ruff 0.17.4 aktiviert standardmäßig 407 Regeln (gezählt mit ruff check --show-settings), unter anderem aus Pyflakes (F), pyupgrade (UP), flake8-bugbear (B) und isort (I) [Ruff-defaults]. Die Version muss deshalb festgeschrieben werden.
  • Projektkonfiguration. Ruff liest pyproject.toml, ruff.toml und .ruff.toml: „For each file, Ruff uses the “closest” config file in the directory hierarchy.“ [Ruff-config] Die Option --isolated bedeutet laut Hilfe: „Ignore all configuration files“.

6.3 Testergebnisse

  • Unbenutzter Import: wurde entfernt (Regel F401, sichere Korrektur).
  • Unbenutzte lokale Variable: wurde gemeldet, aber nicht entfernt (Regel F841). Der Grund laut Dokumentation: „This rule’s fix is marked as unsafe because removing an unused variable assignment may delete comments that are attached to the assignment.“ [Ruff-F841] Erst --unsafe-fixes würde sie entfernen.

6.4 --isolated braucht --target-version

Testprojekt: requires-python = ">=3.8" und eigene [tool.ruff]-Einstellungen.

Ohne Zielversion schrieb Ruff Optional[int] zu int | None und List[int] zu list[int] um. Dieser Code scheitert unter Python 3.8.20 schon beim Definieren der Funktion:

  • TypeError: unsupported operand type(s) for |: 'type' and 'NoneType'
  • TypeError: 'type' object is not subscriptable

Die Projektkonfiguration zu ignorieren, darf deshalb nie dazu führen, dass die Sprachversion des Projekts verloren geht.

7 C und C++

7.1 Formatter: clang-format

7.1.1 Festlegung

Basis ist der LLVM-Stil mit vier Änderungen:

clang-format -i --style="{BasedOnStyle: LLVM, ColumnLimit: 100, IndentWidth: 4, AccessModifierOffset: -4, SortIncludes: false}" <dateien>

7.1.2 Begründung und Belege

  • LLVM-Stil. Der LLVM-Stil ist „A style complying with the LLVM coding standards“ [ClangFormat], [LLVM-CS]. Die Standardwerte stammen aus --dump-config von clang-format 22.1.8:
    • ColumnLimit: 80, IndentWidth: 2, AccessModifierOffset: -2;
    • ContinuationIndentWidth: 4, BreakBeforeBraces: Attach, UseTab: Never.
  • AccessModifierOffset: -4.
    • Im LLVM-Stil stehen public: und private: auf derselben Spalte wie class, denn der Abstand -2 entspricht genau einer Einrückungsstufe (2).
    • Mit IndentWidth: 4 und dem LLVM-Wert -2 stünden sie im Test um 2 Spalten eingerückt, also eine halbe Stufe.
    • Mit -4 standen sie wieder auf der Spalte von class bzw. struct, auch in einer verschachtelten Struktur.
    • Das ist eine Entscheidung und keine Regel: Clangs vordefinierter Microsoft-Stil kombiniert IndentWidth: 4 mit AccessModifierOffset: -2.
  • Keine weitere Anpassung nötig. Die übrigen Einrückungswerte des LLVM-Stils (ContinuationIndentWidth, ConstructorInitializerIndentWidth) sind bereits 4, und PPIndentWidth: -1 folgt IndentWidth.
  • SortIncludes. Die Dokumentation führt die Option inzwischen als Struktur: „Never is deprecated by Enabled: false“ [ClangFormat]. clang-format 22.1.8 akzeptiert SortIncludes: false weiterhin und macht daraus SortIncludes: {Enabled: false}.
  • Projektkonfiguration.
    • Der Stil wird direkt im Befehl übergeben. Eine .clang-format des Projekts (im Test im Google-Stil) hatte dadurch keine Wirkung.
    • Eine .clang-format-ignore des Projekts wirkte trotzdem: Die dort genannte Datei blieb unformatiert. Erst nach dem Ausblenden der Ignore-Datei wurde sie formatiert. Das Tool blendet .clang-format-ignore deshalb während des Laufs aus.

7.2 Linter: clang-tidy

7.2.1 Festlegung

clang-tidy läuft nach clang-format, ohne --fix und ohne --quiet.

# C und C++ vor C++11
clang-tidy datei.c -p build/ \
  --config="{Checks: '-*,bugprone-*,cert-*,clang-analyzer-*,performance-*'}"

# C++11 und neuer: zusätzlich modernize-*
clang-tidy datei.cpp -p build/ \
  --config="{Checks: '-*,bugprone-*,cert-*,clang-analyzer-*,performance-*,modernize-*'}"

7.2.2 Begründung und Belege

  • Kompilierungsdatenbank. „-p is used to read a compile command database.“ [ClangTidy] Ohne compile_commands.json kennt clang-tidy weder die Include-Pfade noch die Makros oder den Sprachstandard. Das -std=-Flag darin entscheidet über die Check-Liste.

  • --config statt Projektdatei. clang-tidy sucht nur dann nach .clang-tidy-Dateien, wenn --config leer ist [ClangTidy]. Im Test unterdrückte eine .clang-tidy des Projekts mit Checks: '-*' ohne --config alle Befunde; mit --config hatte sie keine Wirkung.

  • Ohne --quiet. --quiet unterdrückt laut Dokumentation nur Statistiken [ClangTidy]. Im Test waren die Befunde mit und ohne --quiet identisch; es fielen nur diese Zeilen auf stderr weg:

    6 warnings generated.
Suppressed 4 warnings (3 in non-user code, 1 NOLINT).

    Die Zahl der NOLINT-Unterdrückungen zeigt, wie viele Befunde die Entwickler des Projekts selbst ausgeblendet haben. Das Tool speichert stderr deshalb mit.

  • Aufteilung nach Sprachstandard. In einer Testdatei meldete modernize-* mit -std=c++98 keinen Befund und mit -std=c++17 vier. clang-tidy schaltet diese Checks in diesem Test für Code vor C++11 also selbst ab. Die Aufteilung in zwei Check-Listen entspricht damit dem, was clang-tidy ohnehin tut.

  • modernize-* enthält reine Stil-Checks.

    • modernize-use-trailing-return-type meldete beide Funktionen der Testdatei, also 2 der 4 Befunde (die anderen beiden kamen von modernize-use-nullptr).
    • Im Pilotlauf mit der früheren, umfangreicheren Konfiguration (Kapitel 7.2.4) entfielen bei tinyxml2 223 von 440 Befunden allein auf modernize-use-nullptr.

7.2.3 Warum ohne --fix

Getestet wurde an einem kleinen C++17-Projekt (eine Header-Datei, zwei Quelldateien) mit der Check-Liste für C++11 und neuer:

  • Die Korrekturen waren fast nur Stil. --fix wandte 19 Korrekturen an („clang-tidy applied 19 of 19 suggested fixes“), alle aus modernize-*:
    • 5 nachgestellte Rückgabetypen, auch auto main() -> int;
    • 3 [[nodiscard]]-Attribute;
    • 2 nullptr;
    • je einmal using statt typedef, emplace_back, auto und eine bereichsbasierte for-Schleife.
    Der Code kompilierte danach weiter, aber jede Funktionssignatur des Projekts war umgeschrieben.
  • Keine Unterscheidung zwischen sicheren und unsicheren Korrekturen. Ruff und Biome wenden standardmäßig nur sichere Korrekturen an. clang-tidy kennt nur die Optionen --fix, --fix-errors und --fix-notes [ClangTidy] und damit keine solche Unterscheidung.
  • Abhängig von einer vollständigen Build-Umgebung. Bei einer Datei mit fehlendem Header änderte clang-tidy nichts: „Found compiler errors, but -fix-errors was not specified.“ Ob Code geändert wird, hinge also davon ab, wie vollständig der Container den Build eines Projekts nachbilden kann.
  • Korrigierter Code wird nicht formatiert. --format-style ist standardmäßig none [ClangTidy]. Die Schleifenkorrektur schrieb auto & name, was clang-format anschließend korrigieren müsste.

Möglich, aber nicht festgelegt: Mit --export-fixes=<datei> schrieb clang-tidy alle 19 Korrekturvorschläge in eine YAML-Datei, ohne Dateien zu ändern. Laut Hilfe können sie später „with clang-apply-replacements“ angewendet werden.

7.2.4 Verworfene Alternative: umfangreiche Check-Auswahl

Zunächst wurde eine aus Standards (SEI CERT, C++ Core Guidelines) abgeleitete Konfiguration erstellt: 209 Checks für C und 303 für C++.

Pilotprojekt Version, Standard Befunde
cJSON v1.7.18, -std=c99 25
tinyxml2 11.0.0, -std=c++17 440

Bei tinyxml2 entfielen 63 % der Befunde auf zwei Checks: modernize-use-nullptr (223) und cppcoreguidelines-explicit-virtual-functions (55).

Die Konfiguration wurde zugunsten der hier festgelegten kurzen Check-Liste verworfen. Begründung: vom Autor zu ergänzen.

8 Rust

8.1 Festlegung

CLIPPY_CONF_DIR=<tool>/clippy cargo clippy --fix --allow-dirty && cargo fmt -- --config-path <tool>/rustfmt

<tool>/clippy/clippy.toml und <tool>/rustfmt/rustfmt.toml sind leer.

8.2 Begründung und Belege

  • rustfmt. „By default, Rustfmt uses a style which conforms to the Rust style guide“ [rustfmt], [Rust-style].
  • Clippy.
    • Standardmäßig laufen die Lints der Gruppe clippy::all [Clippy-usage].
    • Zu deren Qualität schreibt die Dokumentation: „We try to keep the warn-by-default groups free from false positives (FP).“ [Clippy-usage]
    • „Note that --fix implies --all-targets, so it can fix as much code as it can.“ [Clippy-usage]

8.3 Testergebnisse

  • Reihenfolge. Die ursprünglich festgelegte Reihenfolge cargo fmt && cargo clippy --fix scheiterte.
    • Nachdem cargo fmt eine Datei geändert hatte, verweigerte Clippy die Arbeit: „error: the working directory of this package has uncommitted changes, and cargo fix can potentially perform destructive changes; if you’d like to suppress this error pass --allow-dirty“.
    • Clippy läuft deshalb zuerst. --allow-dirty („Fix code even if the working directory has changes“ [Cargo-fix]) stellt sicher, dass es auch nach Änderungen anderer Werkzeuge läuft; der saubere Stand aus Schritt 1 liegt weiter in Git.
    • Danach formatiert rustfmt auch den von Clippy geänderten Code.
  • Korrekturen. Clippy ersetzte vec![1, 2, 3] durch ein Array, v.len() == 0 durch v.is_empty() und entfernte .clone() auf einem Copy-Wert.
  • Projektcode wird ausgeführt. Cargo übersetzt Build-Skripte und führt sie aus: „Placing a file named build.rs in the root of a package will cause Cargo to compile that script and execute it just before building the package.“ [Cargo-build-scripts] Clippy läuft deshalb im Container.
  • Projektkonfiguration. Testprojekt: clippy.toml (too-many-arguments-threshold = 10), rustfmt.toml (hard_tabs = true) und [lints.clippy] len_zero = "allow" in der Cargo.toml.
    • clippy.toml: CLIPPY_CONF_DIR ist die erste Stelle, an der Clippy sucht [Clippy-config]. Der Ordner muss eine clippy.toml enthalten, sonst sucht Clippy in den übergeordneten Ordnern weiter. Mit Projektkonfiguration wurde too_many_arguments nicht gemeldet, mit CLIPPY_CONF_DIR schon.
    • rustfmt.toml: --config-path „Recursively searches the given path for the rustfmt.toml config file. If not found reverts to the input file path“ (rustfmt --help). Mit der Projektdatei wurde mit Tabs eingerückt, mit --config-path mit 4 Leerzeichen.
    • [lints] in der Cargo.toml bleibt wirksam: len_zero blieb auch mit CLIPPY_CONF_DIR unterdrückt. Nur ein ausdrückliches -- -W clippy::len_zero holte den Lint zurück.

9 Projektkonfiguration

9.1 Entscheidung

Die Konfigurationsdateien des analysierten Projekts werden immer ignoriert, damit die Ergebnisse verschiedener Projekte vergleichbar sind. Das entspricht der Vorgabe „Fixed rules per language“ im Ablaufdiagramm.

„Ausgeblendet“ heißt: Das Tool verschiebt die Dateien vor dem Lauf aus dem Projekt heraus und legt sie danach zurück, auch wenn ein Werkzeug abbricht.

Eine Ausnahme ist die .gitignore. Biome liest sie bewusst, damit von Git ignorierte Ordner wie Build-Ausgaben nicht formatiert werden (Kapitel 5.4).

9.2 Nicht ignorierbar

Einige Einstellungen lassen sich nur durch Ändern von Projektdateien abschalten. Das Tool vermerkt im Bericht, wenn sie vorhanden sind:

  • Analyzer-Einstellungen in .NET-Projektdateien, etwa <AnalysisMode> (getestet, Kapitel 3);
  • die [lints]-Tabelle in der Cargo.toml (getestet, Kapitel 8);
  • Unterdrückungen im Code selbst, etwa // NOLINT, // NOPMD, # noqa oder #[allow(...)]. Sie gehören zum Code, nicht zur Konfiguration.

10 Grenzen und offene Punkte

  • Kleine Beispieldateien statt echter Projekte: Wie viele Befunde auf echten Projekten entstehen und wie viele davon Fehlalarme sind, wurde nicht gemessen. Dafür wäre ein Pilotlauf pro Sprache auf echten Open-Source-Projekten nötig.
  • Standardwerte der Hersteller: Die Standardregeln sind von den Herstellern gewählt und nicht an den analysierten Projekten geprüft. Ausnahme ist Clippy, dessen Dokumentation für die standardmäßig warnenden Gruppen ausdrücklich Fehlalarmfreiheit anstrebt.
  • Fehlende Typinformationen bei PMD: Ohne Build-Klassenpfad sind einzelne Fehlalarme oder übersehene Befunde möglich (Kapitel 4).
  • dotnet format ohne Konfiguration wendet nur wenige Analyzer-Korrekturen an und ersetzt keinen vollständigen Linter (Kapitel 3).
