Prüfung der Tests

Dokumentation der Werkzeugauswahl für Schritt 5 des Code-Analysis-Tools

Autor:in

Felix Krauß

Veröffentlichungsdatum

13. November 2026

1 Zweck und Vorgehen

Dieses Dokument hält fest, wie das Code-Analysis-Tool in Schritt 5 („Tests“) die Tests eines Projekts prüft. Zu jeder Festlegung steht, warum sie getroffen wurde und wie sie überprüft wurde. Die knappe technische Beschreibung ohne Begründungen liegt im Tool-Repository unter Code-Analysis-Tool/docs/testAnalysis/README.md.

Schritt 5 hat laut Ablaufplan vier Teile. Sie werden nacheinander umgesetzt:

  1. Tests erkennen („Tests present?“): umgesetzt (Kapitel 3).
  2. Tests ausführen („Document results, including failures“): umgesetzt (Kapitel 4).
  3. Testabdeckung messen („no minimum coverage“): umgesetzt (Kapitel 5).
  4. Mutation Testing: umgesetzt (Kapitel 6).

Die Entscheidungen vom 13.11.2026, die die Teile 2 bis 4 bestimmen, stehen in Kapitel 7.

1.1 Grundsatz der Festlegung

  • Konventionen der Frameworks statt eigener Regeln: Ob ein Projekt Tests hat, entscheidet das Tool nach den Standardkonventionen der Test-Frameworks der jeweiligen Sprache, wie sie deren Dokumentation beschreibt. Projektspezifische Konfiguration wird nur gelesen, wo das Framework sie selbst als Ort für die Testerkennung vorsieht (pytest: python_files).
  • Nichts ausführen: Teil 1 liest nur Dateien. Er führt keinen Code des Projekts aus und verändert nichts. Wie viele Tests es genau gibt und ob sie bestehen, ergibt erst Teil 2.
  • Ohne Tests im Bericht vermerken: Hat eine Sprache keine Tests, steht das in der Ausgabe und im Ergebnis, wie im Ablaufplan vorgesehen („no → Note in report“).
  • Werkzeug des Projekts, Optionen vom Tool: Die Tests laufen mit dem Framework bzw. Build-Werkzeug des Projekts. Das Tool legt nur die Optionen fest, die einen maschinenlesbaren Bericht erzeugen. So bleibt das Ergebnis das der Tests des Projekts, und die Berichte sind trotzdem einheitlich auswertbar („Project tool or defined per language“ im Ablaufplan).
  • Tests ohne Netzwerk: Tests führen Code des Projekts aus. Sie laufen deshalb ohne Netzwerk; nur das Herunterladen der Abhängigkeiten davor hat Netzwerk. Das Netzwerk für die Tests lässt sich in code-analysis.toml ([tests] network) einschalten, nur für Code, dem man vertraut (Entscheidung vom 13.11.2026).
  • Fehlschlagende Tests sind Ergebnisse: Ein fehlschlagender Test ist ein Befund über das Projekt, kein Fehler des Tools. Schritt 5 gilt nur dann als unvollständig, wenn Tests gar nicht laufen konnten.

1.2 Prüfmethode

  1. Dokumentation im Original: Jede Konvention wurde in der offiziellen Dokumentation des Frameworks nachgelesen. Zitate sind wörtlich und stehen in der Originalsprache (Englisch).
  2. Eigene Tests:
    • Die Erkennung wurde am 13.11.2026 mit Unit-Tests auf kleinen Beispielprojekten je Sprache geprüft (scheduler/tests/test_testing_detect.py, 16 Tests). Jeder Test enthält auch Gegenbeispiele, die nicht als Test gelten dürfen.
    • Das Ausführen wurde am 13.11.2026 in Docker mit festen Versionen (Tabelle 1) auf einem Mac mit Apple Silicon (arm64) getestet (Colima, Docker 29.5.2): je Sprache ein kleines Projekt mit einem bestandenen, einem fehlschlagenden und einem übersprungenen Test (scheduler/tests/test_testing_docker.py, 10 Tests). Die Berichte dieser Läufe sind die Testdaten der Parser (scheduler/tests/fixtures/testing/).
  3. Echte Projekte: die Spiele-Engine libgdx (Commit 464116b74) und das Repository des Tools selbst (Kapitel 3.3, Kapitel 4.3).

1.3 Testumgebung

Teil 1 braucht keine Container und keine Werkzeuge. Er läuft im Scheduler (Python 3.13) und liest die Dateien, die git kennt. Wie in den Schritten 2 bis 4 werden die Ordner übersprungen, die Schritt 1 überspringt (u. a. node_modules/, build/, target/, vendor/, third_party/, versteckte Ordner).

Teil 2 läuft in einem Test-Image je Sprache:

  • Eigene Images: Die Test-Images sind eigene Images und keine Erweiterung der Images aus den Schritten 2 bis 4. Die Werkzeuge dieser Schritte behalten so ihre Versionen.
  • Volle Basis-Images: Python, Node.js und Rust nutzen die vollen Basis-Images statt -slim. Viele Pakete bauen bei der Installation nativen Code (Python-sdists, node-gyp, build.rs) und brauchen dafür einen Compiler.
  • Zur Laufzeit geladen (Teile 3 und 4): coverage.py 7.17.3 (in die Umgebung des Projekts, falls es keines hat), @vitest/coverage-v8 in der Version des Vitest im Projekt, JaCoCo 0.8.16 (über Maven bzw. Gradle), coverlet.collector 10.1.0 (in die Kopie des Testprojekts), mutmut 3.8.1, StrykerJS 10.1.1 mit Runner, PIT 1.30.2 mit pitest-junit5-plugin 1.2.3 und gradle-pitest-plugin 1.19.0. Sie gehören in die Umgebung bzw. den Build des Projekts und werden im Vorlauf mit Netzwerk geladen.
  • Ältere .NET-Runtimes: Das .NET-Image enthält zusätzlich die Runtimes 8 und 9. Ein Testprojekt läuft auf der Runtime seines Zielframeworks; ohne sie würde ein net8.0-Testprojekt nicht starten.

2 Übersicht der Festlegungen

3 Teil 1: Tests erkennen

3.1 Festlegung

Testeinheiten. Eine Testeinheit („Suite“) umfasst die Tests einer Build-Einheit. Die Einheiten ergeben sich aus den Paketmanagern, die Schritt 1 gefunden hat:

  • Python: der oberste Ordner mit einem Manifest. Ein Manifest in requirements/ zählt für den Ordner darüber.
  • JavaScript und TypeScript: jede package.json. Eine Datei gehört zur nächsten package.json darüber.
  • Java: der oberste Maven- oder Gradle-Build. Es ist dieselbe Regel wie beim Bauen für SonarQube in Schritt 3.
  • C#: jedes Testprojekt.
  • Rust: das oberste Cargo.toml, also der Workspace.
  • C/C++: das CMakeLists.txt im Projektordner. Das ist dieselbe Voraussetzung wie für die Kompilierungsdatenbank in Schritt 2.

Eine Sprache ohne Paketmanager wird nicht geprüft, ebenso C/C++ ohne CMakeLists.txt im Projektordner. Beides steht mit Grund im Ergebnis.

Erkennung je Sprache:

  • Python:
    • Testdateien sind Dateien, deren Name zu pytests python_files passt (Standard test_*.py und *_test.py) und die Testfunktionen, einfache Test…-Klassen oder import pytest enthalten.
    • Dazu kommen Dateien nach unittests Muster test*.py mit unittest.TestCase-Klassen, die test…-Methoden haben.
    • Die pytest-Konfiguration wird in pytests eigener Reihenfolge gesucht: pytest.toml, .pytest.toml, pytest.ini, .pytest.ini, pyproject.toml, tox.ini, setup.cfg. Ihr python_files ersetzt die Standardmuster.
  • JavaScript/TypeScript:
    • Testdateien heißen *.test.*, *.spec.*, *-test.*, *_test.*, test-*.*, test.*, spec.* oder *.cy.*, oder sie liegen in einem Ordner __tests__/ oder test/.
    • Sie müssen describe(, it(, test( oder suite( aufrufen. So zählen etwa Testdaten in test/fixtures/ nicht.
    • Die Frameworks ergeben sich aus dem Testskript und den Abhängigkeiten in der package.json. Das Platzhalter-Skript von npm init zählt nicht als Test.
  • Java:
    • Testdateien importieren JUnit (org.junit…, junit.framework…) oder TestNG (org.testng…).
    • Sie enthalten eine Testannotation (@Test, @ParameterizedTest, @RepeatedTest, @TestFactory, @TestTemplate) oder erben von TestCase.
    • Der Ordner spielt keine Rolle.
  • C#:
    • Ein Testprojekt ist eine .csproj mit <IsTestProject>true</IsTestProject>, mit Sdk="MSTest.Sdk" oder mit einer Paketreferenz auf Microsoft.NET.Test.Sdk, xUnit, NUnit, MSTest oder TUnit. <IsTestProject>false</IsTestProject> schließt ein Projekt aus.
    • Testdateien sind .cs-Dateien des Testprojekts mit Testattributen wie [Fact], [Theory], [Test], [TestCase], [TestMethod], [TestClass] oder [TestFixture].
  • Rust:
    • Integrationstests sind Dateien im Ordner tests/ einer Crate mit #[test]; Varianten wie #[tokio::test], #[rstest] und #[test_case] zählen mit.
    • Unit-Tests sind Quelldateien mit solchen Tests.
    • Doctests sind Rust-Codeblöcke in Doc-Kommentaren (///, //!) von Bibliotheks-Crates. Ein Codeblock gilt als Rust, wenn er keine Sprache oder nur rustdoc-Attribute angibt.
  • C/C++:
    • Tests sind vorhanden, wenn ein CMakeLists.txt oder eine *.cmake-Datei Tests bei CTest registriert (add_test, gtest_discover_tests, gtest_add_tests, catch_discover_tests, doctest_discover_tests) und das Testen mit enable_testing() oder include(CTest) eingeschaltet ist.
    • Testdateien binden den Header eines Test-Frameworks ein oder liegen in einem Ordner test/, tests/, unittest/ oder unittests/.

Testdateien und Quelldateien. - test_files enthält Dateien, die nur Tests sind. Teil 3 lässt sie aus der Testabdeckung heraus. - Rusts Unit-Tests und Doctests stehen in Quelldateien. Diese Dateien werden getrennt geführt (inline_test_files) und bleiben in der Abdeckung.

3.2 Begründung und Belege

Python. - pytest sucht „In those directories, search for test_*.py or *_test.py files“ und sammelt daraus „test prefixed test functions or methods outside of class“ sowie Methoden in „Test prefixed test classes (without an __init__ method)“ [pytest-discovery]. - Zusätzlich gilt: „Within Python modules, pytest also discovers tests using the standard unittest.TestCase subclassing technique.“ [pytest-discovery] - Deshalb ist pytest der Maßstab. pytest führt auch unittest-Tests aus, umgekehrt gilt das nicht. - Die Muster sind einstellbar: „You can configure different naming conventions by setting the python_files, python_classes and python_functions in your configuration file.“ [pytest-naming] - Für die Konfigurationsdatei gilt pytests Reihenfolge: „Look for pytest.toml, .pytest.toml, pytest.ini, .pytest.ini, pyproject.toml, tox.ini, and setup.cfg files“, „The files are considered in the order above.“ und „Options from multiple configfiles candidates are never merged - the first match wins.“ [pytest-config] - pytest.toml und pytest.ini zählen auch leer („will always match and take highest precedence, even if empty“). pyproject.toml zählt nur, wenn es „a [tool.pytest] or [tool.pytest.ini_options] table“ enthält; tox.ini und setup.cfg nur mit „a [pytest] section“ bzw. „a [tool:pytest] section“ [pytest-config]. - unittest erkennt Testdateien am Muster „-p, –pattern pattern: Pattern to match test files (test*.py default)“ und Tests an der Namenskonvention: „A test case is created by subclassing unittest.TestCase. The three individual tests are defined with methods whose names start with the letters test.“ [py-unittest]

JavaScript und TypeScript. Die Dateimuster sind die Vereinigung der Standardmuster der verbreiteten Test-Runner:

  • Jest: Standard ist [ "**/__tests__/**/*.?([mc])[jt]s?(x)", "**/?(*.)+(spec|test).?([mc])[jt]s?(x)" ], also „.js, .jsx, .ts and .tsx files inside of __tests__ folders, as well as any files with a suffix of .test or .spec […] It will also find files called test.js or spec.js.“ [jest-testmatch]
  • Vitest: Standard ist ['**/*.{test,spec}.?(c|m)[jt]s?(x)'] [vitest-include].
  • Node.js-Test-Runner:
    • Er sucht „By default“ nach **/*.test.{cjs,mjs,js}, **/*-test.{cjs,mjs,js}, **/*_test.{cjs,mjs,js}, **/test-*.{cjs,mjs,js}, **/test.{cjs,mjs,js} und **/test/**/*.{cjs,mjs,js} [node-test].
    • Ohne --no-experimental-strip-types gelten dieselben Muster auch für .ts, .cts und .mts [node-test].
  • Mocha: „By default, mocha looks for the glob "./test/*.{js,cjs,mjs}"“ [mocha-globs].
  • Cypress: Die Option specPattern hat den Standard cypress/e2e/**/*.cy.{js,jsx,ts,tsx}: „A String or Array of glob patterns of the test files to load.“ [cypress-config]
  • npm-Platzhalter: npm init schreibt "test": "echo \"Error: no test specified\" && exit 1" [npm-init]. Das ist kein Test und wird ignoriert.

Weil Ordner wie test/ auch Testdaten und Hilfsdateien enthalten, zählt eine Datei nur, wenn sie eine der Testfunktionen aufruft. Die Muster sind eine Obermenge der Standardmuster: Ein Projekt, das seinen Runner anders konfiguriert, kann Dateien haben, die hier zählen, die der Runner aber nicht ausführt. Die genaue Zahl liefert Teil 2.

Java. - Die Erkennung richtet sich nach dem Inhalt der Dateien statt nach dem Ordner src/test/java, wie es auch Gradle tut: „By default, Gradle will run all tests that it detects, which it does by inspecting the compiled test classes.“ [gradle-testing] - Für JUnit 3 und 4 gilt eine Klasse dort als Test, wenn sie „Ultimately inherits from TestCase or GroovyTestCase“, „Is annotated with @RunWith“ oder „Contains a method annotated with @Test or a super class does“ [gradle-testing]. - Für TestNG gilt: „For TestNG, Gradle scans for methods annotated with @Test.“ [gradle-testing] - Die Annotationen bedeuten in JUnit Jupiter „@Test is used to signal that the annotated method is a test method.“ (Paket org.junit.jupiter.api) [junit5-test] und in JUnit 4 „The Test annotation tells JUnit that the public void method to which it is attached can be run as a test case.“ [junit4-test]. - Dass zusätzlich ein Import von JUnit oder TestNG nötig ist, schließt eigene Annotationen gleichen Namens aus (siehe libgdx, Kapitel 3.3). - Das Framework wird aus dem Import abgeleitet: org.junit.jupiter steht für JUnit Jupiter, sonstiges org.junit. für JUnit 4, junit.framework für JUnit 3. Laut JUnit gilt „JUnit Vintage provides a TestEngine for running JUnit 3 and JUnit 4 based tests on the platform.“ [junit-guide]

C#. - „The IsTestProject property is set to true by the Microsoft.NET.Test.Sdk NuGet package. It signifies whether a project is a VSTest test project so that it’s recognized by dotnet test.“ [ms-props] - MSTest.Sdk referenziert dieses Paket selbst („MSTest.Sdk references the Microsoft.NET.Test.Sdk NuGet package“) [ms-props]. - Im Beispiel der Dokumentation von dotnet test steht: „Microsoft.NET.Test.Sdk is the test host, xunit is the test framework.“ [ms-dotnet-test] - Das Framework ergibt sich deshalb aus den Paketreferenzen.

Rust. - Unit-Tests: „You’ll put unit tests in the src directory in each file with the code that they’re testing. The convention is to create a module named tests in each file to contain the test functions and to annotate the module with cfg(test).“ [rust-book-org] - Integrationstests: „We create a tests directory at the top level of our project directory, next to src. Cargo knows to look for integration test files in this directory.“ [rust-book-org] - Hilfsdateien in Unterordnern zählen nicht: „Naming the file this way tells Rust not to treat the common module as an integration test file.“ [rust-book-org] - cargo test führt alle drei Arten aus: „Compile and execute unit, integration, and documentation tests.“ [cargo-test] - Doctests kommen nur aus Bibliotheken: „It extracts code samples from documentation comments of the library target, and then executes them.“ [cargo-test] - Welche Codeblöcke Rust sind: „by default, if no language is set for the block code, rustdoc assumes it is Rust code“ und „unless you specify rust or something that isn’t an attribute (except for custom), the code block is assumed to be Rust source code“ [rustdoc-doctests]. - Die rustdoc-Attribute (ignore, should_panic, no_run, compile_fail, edition…, standalone_crate, test_harness) stehen ebenda [rustdoc-doctests].

C/C++. - Es gibt keinen Standard-Testrunner der Sprache. Die Projekte, die Schritt 1 annimmt (Conan, vcpkg), bauen typischerweise mit CMake, dessen Testrunner CTest ist: add_test „Add a test to the project to be run by ctest(1).“ [cmake-add-test] - Registrierung allein genügt nicht: „CMake only generates tests if the enable_testing() command has been invoked.“ [cmake-add-test] - include(CTest) schaltet das Testen ein; die Option BUILD_TESTING wählt aus, „whether include(CTest) calls enable_testing(). The option is ON by default when created by the module.“ [cmake-ctest] - GoogleTest-Tests werden über das Modul GoogleTest registriert: gtest_add_tests „Automatically add tests with CTest by scanning source code for Google Test macros“, gtest_discover_tests „Automatically add tests with CTest by querying the compiled test executable for available tests“ [cmake-gtest].

3.3 Testergebnisse

Unit-Tests (scheduler/tests/test_testing_detect.py): 16 Tests, alle bestanden. Geprüft werden unter anderem:

  • Python:
    • Eine Datei tests/test_helpers.py ohne Tests zählt nicht.
    • Eine Django-artige app/tests.py mit unittest.TestCase zählt.
    • python_files aus pytest.ini ersetzt die Standardmuster.
    • pytest.toml hat Vorrang vor pyproject.toml.
  • JavaScript/TypeScript:
    • test/fixtures/data.js ohne Testaufrufe zählt nicht.
    • Das npm-Platzhalterskript ergibt „keine Tests“.
    • Ein Testskript ohne bekanntes Framework (eslint .) wird vermerkt.
  • Java:
    • Eine Hilfsklasse in src/main mit JUnit-Import, aber ohne Test, zählt nicht.
    • Tests in einem eigenen Ordner test/ (nicht src/test/java) zählen.
    • Android-Instrumentierungstests werden vermerkt.
  • C#:
    • Ein Projekt mit <IsTestProject>false</IsTestProject> wird ausgeschlossen.
    • MSTest.Sdk wird erkannt.
    • Ohne Testprojekt gibt es einen Eintrag „keine Tests“.
  • Rust:
    • tests/common/mod.rs zählt nicht.
    • Ein ```text-Block zählt nicht als Doctest, ebenso wenig ein Codeblock in einer Binär-Crate.
  • C/C++:
    • Ein add_test in third_party/ zählt nicht.
    • add_test ohne enable_testing() wird vermerkt.

libgdx (Commit 464116b74, Gradle, 2448 Java-Dateien): - Das Tool findet eine Suite (Gradle, settings.gradle) mit 32 Testklassen, Framework JUnit 4. - Die Tests liegen in gdx/test/, einem in Gradle eigens eingestellten Ordner (nicht src/test/java). Die Erkennung über den Inhalt findet sie trotzdem. - git grep findet 33 Java-Dateien mit @Test. Die 33. ist tests/gdx-tests/src/com/badlogic/gdx/tests/AnnotationTest.java, eine Demo der Engine ohne JUnit-Import. Sie wird zu Recht nicht gezählt. - Die übrigen Klassen unter tests/ sind Demo-Anwendungen der Engine, keine automatisierten Tests, und zählen ebenfalls nicht. - C/C++ (vorhanden, aber ohne Conan/vcpkg) wird als „nicht geprüft: kein Paketmanager“ ausgewiesen.

Repository des Tools: eine Python-Suite (scheduler/pyproject.toml) mit pytest-Konfiguration, pytest als Abhängigkeit und 22 Testdateien. Das entspricht den Dateien scheduler/tests/test_*.py.

3.4 Grenzen

  • Statisch: Teil 1 zählt Dateien, keine Tests. Projektkonfigurationen der Runner (z. B. testMatch in Jest, testDir in Gradle, eigene Mocha-spec-Muster) werden außer bei pytest nicht ausgewertet. Die genauen Zahlen liefert Teil 2.
  • Vereinigte Muster bei JavaScript: Eine Datei kann als Testdatei zählen, die der konfigurierte Runner nicht ausführt, etwa unter Mochas Standard ./test/* ohne --recursive.
  • C/C++: Nur CMake mit CMakeLists.txt im Projektordner. Andere Build-Systeme (Make, Meson, Bazel) werden nicht geprüft. Projektoptionen, die Tests standardmäßig ausschalten (z. B. option(… TESTS OFF)), erkennt Teil 1 nicht.
  • Sprachen ohne Paketmanager werden nicht geprüft, wie in Schritt 4.

4 Teil 2: Tests ausführen

4.1 Festlegung

Ablauf je Testeinheit. - Jede Suite mit Tests läuft in frischen Containern des Test-Images ihrer Sprache, auf einer Kopie des Projekts. - Die Suites laufen nacheinander, nicht parallel. Die Testwerkzeuge nutzen selbst alle Prozessorkerne, und parallele Läufe könnten zeitkritische Tests scheitern lassen. - Jede Suite durchläuft zwei Phasen: 1. Vorlauf mit Netzwerk: Der Paketmanager lädt die Abhängigkeiten in einen Cache im Ausgabeordner. Wo er das kann, ohne Code des Projekts oder seiner Pakete auszuführen, tut er es (Tabelle 3). 2. Testlauf ohne Netzwerk (--network none): Build und Tests verwenden nur, was der Vorlauf geladen hat. Mit network = true unter [tests] in code-analysis.toml hat auch der Testlauf Netzwerk; das Tool warnt dann.

Befehle: - Python: - Installation in .venv der Kopie mit dem Paketmanager des Projekts: uv sync --frozen --all-extras --all-groups, poetry install --all-extras --all-groups, pdm install -G :all bzw. pipenv sync --dev. - pip-Projekte installiert uv pip install: das Projekt editierbar mit den Extras test, tests, testing oder dev, die gleichnamigen Abhängigkeitsgruppen, requirements.txt und Requirements-Dateien für Tests und Entwicklung. - Fehlt pytest danach, wird pytest 9.2.0 ergänzt. - Test: .venv/bin/python -m pytest --junitxml=<Bericht> --continue-on-collection-errors -p no:cacheprovider. - JavaScript/TypeScript: - Installation ohne Lifecycle-Skripte (npm ci --ignore-scripts, entsprechend Yarn, pnpm, Bun) im Ordner mit dem Lockfile. - Offline laufen dann die Install-Skripte der Pakete (npm rebuild, pnpm rebuild, yarn rebuild) und das Framework mit einem zusätzlichen Reporter: - Vitest --reporter=junit, - Jest --ci --json --outputFile, - Mocha --reporter xunit, - node --test mit --test-reporter=junit, - bun test --reporter=junit. - Ist das Testskript ein einzelner Aufruf des Frameworks, werden dessen Argumente übernommen. - Java: - Maven: mvn -fae test -Dtest='*#codeAnalysisSelectsNoTest' im Vorlauf, dann mvn -o -fae test -Dmaven.test.failure.ignore=true. - Gradle: Ein Init-Skript lädt im Vorlauf die externen Abhängigkeiten aller Konfigurationen und listet die test-Tasks der Java-Projekte. Dann gradle --offline --continue <diese Tasks>. - Ein Wrapper (mvnw, gradlew) des Projekts hat Vorrang. - C#: dotnet restore, dann dotnet test <Testprojekt> --no-restore --logger "trx;LogFilePrefix=results". - Rust: cargo fetch, dann cargo test --workspace --no-fail-fast --offline. - C/C++: - Konfigurieren mit demselben Skript wie in Schritt 2 (Conan oder vcpkg, CMake), aber mit CMAKE_BUILD_TYPE=Debug. - Dann offline cmake --build und ctest --output-junit <Bericht> --output-on-failure.

Zeitlimit: time_limit_minutes unter [tests] in code-analysis.toml gilt je Testbefehl (Standard 60 Minuten, 0 = kein Limit). Der Vorlauf hat 60 Minuten.

Ergebnis je Test: - Eine Kennung, die in beiden Ständen gleich ist. - Das Ergebnis (passed, failed, error, skipped), die Dauer und die gekürzte Fehlermeldung. - Doctests in Rust bekommen eine Kennung ohne Zeilennummer, weil die Formatierung in Schritt 2 Zeilen verschiebt.

Status eines Laufs: - ok: Die Tests liefen und ihr Bericht wurde gelesen; fehlschlagende Tests eingeschlossen. - partial: Ein Teil der Tests lief, oder nur der Exitcode ist bekannt. - failed: Es gibt kein Testergebnis. - skipped: Conda, oder JavaScript-Tests, die einen Browser brauchen.

Zwei Stände (Kapitel 7): - Hat Schritt 2 das Projekt verändert (git status nicht leer), laufen dieselben Suites zusätzlich auf dem Commit-Stand (HEAD). - Die HEAD-Kopie entsteht über einen temporären Git-Index (read-tree, checkout-index). Das Repository des Projekts bleibt unverändert, und anders als bei git archive fehlen keine mit export-ignore markierten Dateien. - Tests mit unterschiedlichem Ergebnis, oder die nur in einem Stand liefen, werden mit dem Hinweis auf mögliche „flaky“ Tests ausgegeben. Ohne Unterschiede wird der Vergleich nicht erwähnt.

4.2 Begründung und Belege

Offline-Testlauf. - Cargo: cargo fetch lädt nur, und danach kann Cargo offline arbeiten: „this command will ensure that all of the git dependencies and/or registry dependencies are downloaded and locally available. Subsequent Cargo commands will be able to run offline after a cargo fetch unless the lock file changes.“ [cargo-fetch] - Gradle: - --offline „Specifies that the build should operate without accessing network resources.“ [gradle-cli] - --continue „Continue task execution after a task failure.“ [gradle-cli]. Ein festes Werkzeug je Sprache:

Zählweise: - Gezählt werden die Quelldateien der Sprache unterhalb der Suite. Nicht dazu gehören: - Testcode: die Testdateien aus Teil 1, Dateien in Testordnern (test/, tests/, __tests__/, spec/, src/test/, …) und conftest.py; - generierte Dateien aus Schritt 1; - Build-Skripte und Werkzeugkonfiguration (setup.py, build.rs, *.config.js, …); - Dokumentation und Beispiele. - Bei C# ist eine Suite ein Testprojekt; gezählt werden die C#-Dateien außerhalb der Testprojekte. - Rusts Quelldateien mit #[cfg(test)]-Modulen zählen samt dieser Module. - Je Datei gibt es: ausführbare Zeilen, davon ausgeführte, Branches (wo das Werkzeug sie meldet) und die nicht ausgeführten Zeilennummern. - Quelldateien ohne Messdaten hat kein Test geladen. Ohne coverage.reportOnFailure („Generate coverage report even when tests fail.“, Standard false) entsteht bei einem fehlschlagenden Test kein Bericht [vitest-coverage]. 6 Teil 4: Mutation Testing

6.1 Festlegung

Ablauf: - Nach der Abdeckung prüft ein Mutationslauf die Tests jeder Suite, in derselben Kopie (Stand nach Schritt 2) und ohne Netzwerk. - Nur das Hinzufügen des Werkzeugs zur Kopie hat Netzwerk. - Jedes Werkzeug arbeitet mit seinen Standard-Mutatoren.

Umfang ([tests.mutation] in code-analysis.toml, bei jedem Start gelesen): - mode = "sample" (Standard): eine Zufallsstichprobe von sample_files (Standard 20) Quelldateien, aus den Dateien mit mindestens einer abgedeckten Zeile aus Teil 3. - Die Stichprobe wird mit festem seed (Standard 1) gezogen; dasselbe Projekt ergibt dieselbe Stichprobe. - Hat eine Suite weniger abgedeckte Dateien, werden alle mutiert. - mode = "full": alle Quelldateien der Suite. - time_limit_minutes (Standard 60, 0 = kein Limit) je Mutationslauf. - Ist das Limit erreicht, wird der Lauf beendet und bekommt partial mit den bis dahin bewerteten Mutanten. - Das eingestellte Limit macht Schritt 5 nicht unvollständig. - Die Einstellungen sind die Entscheidungen des Nutzers vom 13.11.2026 (Kapitel 7).

Ergebnis: - Je Mutant: Datei, Zeile, Mutator, Änderung und Zustand. - Die Zustände folgen dem Schema mutation-testing-elements von Stryker; mutmut, PIT und cargo-mutants werden darauf abgebildet. Die Tabelle steht in Code-Analysis-Tool/docs/testAnalysis/README.md. - Bei nicht erkannten Mutanten (Survived, NoCoverage) wird die Quellzeile mitgespeichert, für die Bewertung in Schritt 6. - Der Score ist (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage).

6.2 Begründung und Belege

Score und Zustände. - Stryker definiert: „Mutation score: detected / valid * 100“. - Zu den Zuständen: „Timeout: […] It is counted as “detected”.“, „Compile error: […] It is not represented in your mutation score.“, ebenso „Runtime error“, und „Ignored: […] This will not count against your mutation score but will show up in reports.“ [stryker-states] - Dieselben Begriffe für alle Sprachen machen die Ergebnisse in Schritt 6 einheitlich lesbar. - PITs Zustände sind dort beschrieben, etwa „No coverage is the same as Survived except there were no tests that exercised the line of code“ und „A non viable mutation is one that could not be loaded by the JVM“ [pit-concepts]. Daraus folgt die Abbildung auf NoCoverage bzw. CompileError.

Fehlschlagende Tests. Alle Werkzeuge brauchen einen Testlauf ohne Mutanten, der besteht:

  • PIT bricht sonst ab: „1 tests did not pass without mutation when calculating line coverage. Mutation testing requires a green suite.“ (eigener Test).
    • Der Plugin-Deskriptor von pitest-maven 1.30.2 beschreibt skipFailingTests: „When set will ignore failing tests when computing coverage. Otherwise, the run will fail.“
    • Der Parameter hat keine Kommandozeilen-Property. Er steht deshalb in der Plugin-Konfiguration, die das Tool in die pom.xml der Kopie schreibt.
    • Auch das JUnit-5-Plugin muss dort stehen: „To activate the plugin it must be placed on the classpath of the pitest tool (not on the classpath of the project being mutated).“ [pit-junit5]
    • excludedTestClasses wäre keine Alternative: „List of globs to match against test class names.“ [pit-maven] Es schließt ganze Klassen aus, nicht einzelne Tests.
  • cargo-mutants prüft zuerst den unveränderten Baum: „This makes sure that your tests are in fact all passing“ [cargo-mutants-baseline]. Andernfalls endet es mit Exitcode 4: „The baseline tests are already failing or hanging before any mutations are applied, so no mutations were tested.“ [cargo-mutants-exit]
    • Argumente nach einem zweiten -- gehen an die Testbinaries: „You can use a second double-dash to pass options through to the test targets.“ [cargo-mutants-args]
    • Damit wird libtests --skip übergeben.
  • mutmut: „for CLI args that select or deselect tests, use pytest_add_cli_args_test_selection“ [mutmut].
    • Die Einstellungen gelten aus [tool.mutmut] der pyproject.toml, wenn es diese Tabelle gibt, sonst aus setup.cfg. So steht es im Quelltext von mutmut 3.8.1 (configuration.py, _config_reader).
    • Das Tool ersetzt daher eine vorhandene Tabelle in der Kopie.
  • Stryker.NET: --test-case-filter „Filter expression to run selective tests.“ [stryker-net-config]
  • StrykerJS hat keine allgemeine Option, einzelne Tests auszuschließen; seine Optionen [stryker-js-config] wählen nur mutierte Dateien (mutate) und den Runner. Suites mit fehlschlagenden Tests werden deshalb nicht mutiert.

Dateiauswahl. - cargo-mutants: „--file GLOB: Mutate only functions in files matching the glob.“ [cargo-mutants-files] - PIT: „targetClasses: The classes to be mutated.“ [pit-maven] - StrykerJS: „With mutate you configure the subset of files or just one specific file to be mutated.“ [stryker-js-config] - Stryker.NET: „With mutate you configure the subset of files to use for mutation testing.“ [stryker-net-config] - Die Stichprobe auf Dateiebene lässt sich deshalb mit allen Werkzeugen gleich umsetzen. - Gezogen wird aus abgedeckten Dateien, weil Mutanten in nie ausgeführtem Code ohne Testlauf NoCoverage sind. Sie zeigen nichts über die Qualität der vorhandenen Tests, was die Abdeckung (Teil 3) nicht schon zeigt. - Fachliteratur zur Stichprobe von Mutanten ist in Quellenvorschlaege.md (Abschnitt F) vorgeschlagen. 6.4 Grenzen

  • Stichprobe auf Dateiebene: Gezogen werden Dateien, nicht einzelne Mutanten. Dateien mit vielen Mutanten wiegen schwerer. Der Score einer Stichprobe ist eine Schätzung für die abgedeckten Dateien, nicht für das ganze Projekt.
  • Zeitlimit: PIT, StrykerJS und Stryker.NET schreiben ihren Bericht erst am Ende. Erreichen sie das Limit, gibt es keine Ergebnisse (partial mit Hinweis).
  • StrykerJS läuft nur, wenn alle Tests bestehen. PIT braucht für TestNG ein weiteres Plugin, das das Tool nicht hinzufügt. Maven-Multimodule: Das Plugin steht in der Wurzel-pom.xml; Module, die nicht von ihr erben, laufen ohne JUnit-5-Plugin. Stryker.NET mutiert bei mehreren referenzierten Projekten nur das mit den meisten ausgewählten Dateien.
  • Vergleichbarkeit: Mutatoren und Zählweise unterscheiden sich je Werkzeug (siehe Testergebnisse). Ein Score ist ein Maß innerhalb einer Sprache.
  • C/C++ wird nicht mutiert.

7 Entscheidungen vom 13.11.2026

Am 13.11.2026 vom Nutzer festgelegt und umgesetzt: Code-Stand und Netzwerk in Teil 2 (Kapitel 4), die Werkzeuge der Abdeckung in Teil 3 (Kapitel 5), Umfang und Zeitlimit des Mutation Testing in Teil 4 (Kapitel 6).

  • Code-Stand:
    • Die Tests laufen auf dem Stand nach Schritt 2, wie die Schritte 3 und 4; das ist das Hauptergebnis.
    • Zusätzlich laufen sie auf dem Commit-Stand (HEAD), und die Ergebnisse je Test werden verglichen. Schritt 2 hinterlässt automatische Korrekturen der Linter, die das Verhalten ändern könnten.
    • Unterschiede kommen in den Bericht, sonst wird der Vergleich nicht erwähnt.
    • Hat Schritt 2 nichts geändert, entfällt der zweite Lauf.
  • Netzwerk:
    • Die Tests führen Code des Projekts aus. Sie laufen deshalb standardmäßig ohne Netzwerk.
    • Nur der Vorlauf, der die Abhängigkeiten herunterlädt, hat Netzwerk.
    • In code-analysis.toml lässt sich das Netzwerk für die Tests einschalten. Das soll man nur tun, wenn man dem Code des Projekts vertraut.
  • Mutation Testing:
    • Standard ist eine reproduzierbare Stichprobe von Dateien mit Zeitlimit; ein vollständiger Lauf ist wählbar.
    • Beides und das Limit in Minuten (0 = kein Limit) stehen in code-analysis.toml.
  • C/C++: Tests und Abdeckung ja. Mutation Testing wird als „nicht unterstützt“ vermerkt.
  • Werkzeuge:
    • Die Tests laufen mit dem Framework bzw. Build-Werkzeug des Projekts, mit vom Tool festgelegten Optionen für maschinenlesbare Berichte.
    • Für die Abdeckung gibt es ein festes Werkzeug je Sprache, damit die Werte vergleichbar sind.
